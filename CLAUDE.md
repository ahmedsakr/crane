# Crane

Crane is an autonomous software factory steered by a human operator. Agents run Claude Code headless (`claude -p`) against git repos. This file is read by humans and by Crane's own agents when they work on Crane ("factory feature" tasks).

## Commands

- `npm run dev`: factory on :4471 + UI with hot reload on :5173
- `npm run typecheck`: backend, tests, scripts, and web
- `npm test`: node:test suites in `test/`
- `npm run build`: transpiles `src/` to `dist/` with esbuild, without bundling (`factoryRoot()` depends on each compiled file's location), and builds `web/dist/`. It doesn't check backend types, so a passing build doesn't mean the types are right: run `npm run typecheck`, which `prepack` and the configured checks do. `scripts/build.mjs` runs `build:packages`, `build:backend`, and web's `build` without starting npm for each one, so edit those scripts rather than adding steps through nested `npm run`. Web's `prebuild` compiles contracts only for `npm run build -w web` on its own, which is what dashboard builds run.
- `npm run build:packages` first checks every workspace's `node_modules/<name>` symlink, then compiles the shared packages. Build, typecheck, test, dev, and `npm run crane -- <cmd>` all run this preflight. If it names missing or incorrect links (often after pulling a new workspace), run `npm install` in your checkout and retry. Crane never runs this repair in the operator's checkout; merges that change a `package.json` or `package-lock.json` leave a task note reminding you to install.
- `npm run crane -- <cmd>`: run the CLI from source, including the workspace preflight and package builds. Direct `npx tsx src/cli/index.ts <cmd>` calls need `npm run build:packages` first.
- `crane start`: in a source checkout, runs `npm run build` and supervises compiled `crane serve` with the same options. Polls checkout HEAD every second; a new commit gracefully stops the factory, rebuilds, and restarts it. No fetch, pull, dependency install, or source-file watching. Initial build failures exit; failed updates wait stopped for another commit or an operator rerun.
- Inspecting live factory state: `npm run --silent crane -- tasks --all --json` gives every task with its status, `branch`, and `worktree` (add `-n 500` for more than 50). The CLI opens the store read-write and runs its migrations, so if your branch changes the schema in `src/core/store.ts`, or you need a table the CLI doesn't show, open `$CRANE_HOME/crane.db` with `better-sqlite3` and `{ readonly: true }` instead. There is no `sqlite3` binary, and Node 20 has no `node:sqlite`. Use Glob/Read for paths under `$CRANE_HOME`, not shell `ls`.
- Demo data: `CRANE_HOME=/tmp/crane-demo npx tsx scripts/seed-demo.ts`, then `serve --driver simulated`
- `npm run screenshot -- <path> [steps] --out <file.png>`: boots a throwaway demo factory and screenshots the built UI in headless Chromium. Steps run in order: `--click <sel>`, `--type <text>`, `--key Escape`, `--wait-for <sel>`, `--eval <js>`, `--shot <file>`. Whole-run options: `--size 390x844` (default `1280x800`) and `--media prefers-color-scheme=dark` (or `prefers-reduced-motion=reduce`). `--size` applies to every capture, regardless of its position; repeating it uses only the last value. Use one invocation per viewport. Run `npm run build -w web` first. Example: `npm run screenshot -- "/?instruct=Fix the tests" --click ".choice-btn" --out .crane/menu.png`

  Task-page example: wait for a loaded task link before navigating, then for task content before capturing. These commands open the first task in each throwaway demo's list; for a specific task or state, choose its link and wait for a selector that identifies the required content. Page load alone does not mean task data has loaded; `--wait-for` waits for a matching element to exist.

  ```sh
  npm run build -w web &&
  npm run screenshot -- /tasks --size 1280x800 --wait-for '.rows a.row' --click '.rows a.row' --wait-for '.detail-title' --out .crane/screenshots/task-wide.png &&
  npm run screenshot -- /tasks --size 1280x600 --wait-for '.rows a.row' --click '.rows a.row' --wait-for '.detail-title' --out .crane/screenshots/task-short.png &&
  npm run screenshot -- /tasks --size 390x844 --wait-for '.rows a.row' --click '.rows a.row' --wait-for '.detail-title' --out .crane/screenshots/task-phone.png
  ```

Captures serve `web/dist`: wait for the UI build to finish successfully before starting any dependent capture. Use `npm run build -w web && npm run screenshot -- ...`; viewport captures may run in parallel only after that successful build. Rebuild after further UI changes.

## Shape

- `src/core/store.ts` is the single source of truth (SQLite, WAL). Every process (server, CLI) opens it directly; there is no in-memory state worth trusting across processes. Live views tail the `events` table.
- `src/factory/actions.ts` holds every operator action. The API and CLI both call it, so add new actions there first.
- `@crane/agent-protocol` (`packages/agent-protocol/`) is what the factory and every driver agree on: `AgentDriver`, `RunContext`, `AgentRunError` (one class; retries check `instanceof`), `isTransientFailure`, `REPORT_FENCE`, `parseReport` and `combinedCost`. It is private and versioned with Crane because `RunContext` carries full `Task` and `Repo` records. It imports only contract types and has one ESM entry point with declarations; its compiler explicitly uses Node types for `AbortSignal`, with no DOM library.
- `@crane/agent-policy` (`packages/agent-policy/`) owns the deny list and permission-rule handling that operator actions and drivers share: `ALWAYS_DENIED`, `isAllowed`, `overlapsDenied` and `suggestRules`. It imports only `@crane/contracts/rules` and exposes one ESM entry point with declarations (`test/boundaries.test.ts`). Its compiler has no Node or DOM ambient types. The command splitter stays internal and is not a shell parser. Rule grammar and labels stay in contracts; each driver keeps its own tool lists and CLI arguments.
- `@crane/agent-drivers` (`packages/agent-drivers/`) holds the concrete drivers behind `AgentDriver`: `ClaudeCodeDriver`, `CodexDriver`, and `SimulatedDriver`, its only public exports. Prompts, CLI helpers, provider pricing, and Codex command-evidence tracking stay private; repository tests may import them through package source paths. It depends only on contracts, agent-protocol, agent-policy, diagnostics, and Node, with `rootDir: src` enforcing the compiler boundary. The simulated driver has a private helper for staging resolved files; Crane's worktree and branch logic stays in `src/factory/git.ts`. Only `src/factory/drivers.ts` imports the package in production and owns the registry because it depends on settings keys (`test/boundaries.test.ts`). A task's `driver` is the operator's pick (null follows the default setting); an interrupted task resumes on the driver of its last work run, which owns its session. Adding an agent means a driver, an entry in `DRIVER_NAMES` (`packages/contracts/src/types.ts`), and one in `createDriver`. Agents end their final message with a fenced `crane-report` JSON block (asked for in `packages/agent-drivers/src/prompts.ts`), parsed by `packages/agent-protocol/src/report.ts`, which owns the fence tag and ignores agent-supplied `validation`.
- Tasks with autonomy `propose`/`act` run in a git worktree under `$CRANE_HOME/worktrees/<taskId>` on branch `crane/<slug>-<id>`. A new worktree starts from the newest of the local and remote default branch (the merge path's rules, after a fetch), never moving either, so a stale or dirty operator checkout can't hide landed work. Before dependency setup or the agent, `createWorktree` holds the task as failed with a diagnostic if the base or a reused worktree lacks a merged prerequisite's commit, or if local and remote have diverged; a reused worktree is only checked, never reset. Diffs and changed-file lists compare with that same newest tip (`comparisonBase`). Crane never pushes or merges on its own. Only an operator's Approve (or Merge) does, and then Crane's own code in `src/factory/merge.ts` lands the branch (merge commit, fast-forward push, local default branch moved only when its checkout is clean). Agents only ever resolve conflicts inside Crane's worktree; they never push or merge.
- Conflict resolution has an editing run followed by a validation run. Between them Crane commits the resolved candidate and retains it under `refs/crane/resolutions/<hashed task id>`; a companion `-nonvisual` ref binds any visual-review opt-out to that exact candidate (missing metadata requires review). Recovery offers that checkpoint to validation only when its two parents exactly match the current default and task commits and the clean worktree is still at the checkpoint. Changed inputs invalidate it; unexpected tracked edits stop recovery without discarding work. Validation may fix the candidate, but all candidate visual decisions and configured merge checks still apply. A checkpoint records edits, never successful validation or operator approval.
- `web/` is React + Vite with no UI library. It shares domain/HTTP shapes, labels, and pure helpers with the backend through the internal `@crane/contracts` workspace (`packages/contracts/`). Its explicit entry point is `src/index.ts`; `@crane/contracts/rules` exposes the minimal rule grammar for backend permission handling. Enforcement stays in `@crane/agent-policy`. Contracts have no runtime dependencies, Node modules, React, storage, or factory implementation. Cross-workspace source imports are forbidden (`test/contracts.test.ts`).
- `@crane/worktree-deps` (`packages/worktree-deps/`) prepares lockfile-based installs and verified dependency copies for the orchestrator, merge checks, and dashboard builds. Its only public function is `installDependencies`, with `InstallDependenciesOptions` for copy source, cancellation, and progress. Fingerprinting, lock comparison, copy mechanics, and package discovery stay internal. It imports only Node modules, `@crane/diagnostics`, and its own implementation, never Store, Task, drivers, or factory code. Application elapsed formatting stays in `src/factory/elapsed.ts`; dependency notes keep their own private duration formatter.
- `@crane/diagnostics` (`packages/diagnostics/`) owns best-effort credential redaction for text about to be stored or shown. Its only public function is `sanitizeDiagnosticText(raw, limit)`, used by agent-drivers' `safeEvidenceText` and worktree-deps' `InstallDiagnostics`, so add credential rules and their `test/diagnostics.test.ts` cases there. It removes control sequences first and applies the limit last, and it hides a sensitive value through the end of its line, which also hides the rest of a command after `TOKEN=x`. It has no imports, no runtime dependencies, and no Node or DOM ambient types. Command tracking, process execution, stream buffering, output tails, and private-key state across chunks stay with their consumers.
- `npm run build:packages` checks workspace links, then compiles the composite package graph in `tsconfig.packages.json` with `tsc -b` before build, typecheck, tests, dev, and the source CLI. Each package references its workspace dependencies and stores its build cache inside `dist/`; `npm run dev` uses one graph watcher for all workspace packages. Run the package build before invoking backend source scripts directly. The root npm tarball bundles all private packages so installed CLI builds need no separate releases. `src/core/webbuild.ts` treats each package's `src/`, `package.json`, and `tsconfig.json` as build inputs by scanning `packages/*`: contracts, the only package the dashboard bundles, affect dashboard and factory staleness; every other package affects only the factory. `test/contracts.test.ts` discovers `packages/*` too and fails if a package is missing from the root `dependencies`, `bundledDependencies`, `workspaces`, or solution references, if project references differ from workspace dependencies, or if a package differs from the standard manifest.

## Rules

- Safety first: nothing an agent does may touch the operator's checkout or default branch. Keep `ALWAYS_DENIED` in `packages/agent-policy/src/denied.ts` intact. Codex has no deny list, so its guard is the sandbox in `codexArgs` (`packages/agent-drivers/src/codex.ts`): read-only for investigate-only, workspace-write with no network and no extra writable roots otherwise. Never loosen it. Every new driver needs an equivalent guard. The one place Crane moves a default branch is `landTask` in `src/factory/merge.ts`, after the operator approves: never force-push, and never touch a checkout that has local changes.
- Keep the CLI and web UI at feature parity for operator actions.
- UI work must follow `docs/design.md`. Progressive disclosure is the core principle: show the decision first, the details one tap away.
- Look at UI changes before calling them done. Take screenshots with `npm run screenshot` (wide 1280x800, short 1280x600, and phone 390x844) and read the PNGs; for visual bugs, reproduce in a screenshot first when capture is available. In a sandbox known to refuse local servers or browsers, defer capture directly without trying it. Report visual validation as outstanding and include the changed views, states, exact capture commands, and sizes in an operator checklist, following [Visual review before approval](README.md#visual-review-before-approval). Before approval or merge, the operator must record inspection of the candidate or an explicit waiver with its reason, unless they pre-approved the task: pre-approval authorizes Crane to record candidate waivers automatically, including conflict resolutions. Agent reports still classify UI work and disclose missing inspection. Passing typecheck, tests, or review and merge checks does not complete visual validation.
- The dashboard on :4471 serves whichever build is newest: Crane's own build of the latest merge to its repo (`$CRANE_HOME/builds/<sha>`, made by `src/factory/dashboard.ts` after each factory-repo merge and on `crane serve`), or the checkout's `web/dist`. If the operator reports that a fixed UI bug is still there, check which build is served (`uiCommit` in `/api/overview`), whether that build failed (a note on the merged task), and whether their tab needs a reload.
- Backend changes need a separate rebuild and restart when `bin/crane.js` runs `dist/`. `/api/overview` reports `factory.factoryOutdated`, and the dashboard shows a notice when the running build is older than its checkout's `src/`. The notice stays until restart even if someone rebuilds on disk. Dashboard builds and page reloads do not update the running backend.
- Copy is sentence case, plain verbs, and names things by what the operator controls. An action keeps its name everywhere ("Approve" → "Approved").
- Finish relevant edits before starting builds, typechecks, or tests, and do not edit their inputs while they run. Direct tests can import compiled workspace `dist` files: after the final relevant edit, await a successful `npm run build:packages` (also included in `npm run typecheck`) before starting dependent direct tests. Further edits or edits overlapping a check invalidate affected local results; rebuild changed packages and rerun dependent checks before reporting a pass for the final code. See [Validation order](docs/testing.md#validation-order).
- Before finishing outside the restricted sandbox, run `npm run typecheck` and `npm test` separately and retain each exit status. In Codex's no-network sandbox, run typecheck and relevant direct-file checks from [Sandbox test selection](docs/testing.md#sandbox-test-selection); defer `npm test` and the complete `test/limits.test.ts`, `test/drivers.test.ts`, and `test/restart.test.ts` suites directly to Crane's existing external review and merge checks without attempting them locally. Report them as not run locally, left to Crane's checks; a local subset is not a full-suite pass. Do not change configured checks or reduce their coverage.
- Codex's no-network filter also refuses `listen` and some local socket calls used for piped child stdio. Known incompatible checks do not need another failed attempt to establish this limitation. Direct-file diagnostics are useful only for files that do not require those capabilities; running a fake-agent suite directly does not remove its piped subprocess requirement. Do not reshape tests, scripts, code, permissions, or sandbox settings to get around restrictions. For an unexpected failure, retain the actual error and follow the refusal/reporting rules; missing stream output alone does not prove a code defect or identify an exact sandbox error.
