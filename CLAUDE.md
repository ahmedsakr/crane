# Crane

Crane is an autonomous software factory steered by a human operator. Agents run Claude Code headless (`claude -p`) against git repos. This file is read by humans and by Crane's own agents when they work on Crane ("factory feature" tasks).

## Commands

- `npm run dev`: factory on :4471 + UI with hot reload on :5173
- `npm run typecheck`: backend, tests, scripts, and web
- `npm test`: node:test suites in `test/`
- `npm run build`: compiles `src/` to `dist/` and builds `web/dist/`
- `npx tsx src/cli/index.ts <cmd>`: run the CLI from source
- Inspecting live factory state: `npm run --silent crane -- tasks --all --json` gives every task with its status, `branch`, and `worktree` (add `-n 500` for more than 50). The CLI opens the store read-write and runs its migrations, so if your branch changes the schema in `src/core/store.ts`, or you need a table the CLI doesn't show, open `$CRANE_HOME/crane.db` with `better-sqlite3` and `{ readonly: true }` instead. There is no `sqlite3` binary, and Node 20 has no `node:sqlite`. Use Glob/Read for paths under `$CRANE_HOME`, not shell `ls`.
- Demo data: `CRANE_HOME=/tmp/crane-demo npx tsx scripts/seed-demo.ts`, then `serve --driver simulated`
- `npm run screenshot -- <path> [steps] --out <file.png>`: boots a throwaway demo factory and screenshots the built UI in headless Chromium. Steps run in order: `--click <sel>`, `--type <text>`, `--key Escape`, `--wait-for <sel>`, `--eval <js>`, `--shot <file>`, `--size 390x844`. Run `npm run build -w web` first. Example: `npm run screenshot -- "/?instruct=Fix the tests" --click ".choice-btn" --out .crane/menu.png`

## Shape

- `src/core/store.ts` is the single source of truth (SQLite, WAL). Every process (server, CLI) opens it directly; there is no in-memory state worth trusting across processes. Live views tail the `events` table.
- `src/factory/actions.ts` holds every operator action. The API and CLI both call it, so add new actions there first.
- `@crane/agent-protocol` (`packages/agent-protocol/`) is what the factory and every driver agree on: `AgentDriver`, `RunContext`, `AgentRunError` (one class; retries check `instanceof`), `isTransientFailure`, `REPORT_FENCE`, `parseReport` and `combinedCost`. It is private and versioned with Crane because `RunContext` carries full `Task` and `Repo` records. It imports only contract types and has one ESM entry point with declarations; its compiler explicitly uses Node types for `AbortSignal`, with no DOM library. `src/agent-protocol/index.ts`, `src/agents/driver.ts`, `report.ts` and `combinedCost` in `codex-pricing.ts` are temporary re-exports of the same package; don't add new imports of them.
- `src/agent-policy/` owns the deny list and permission-rule handling that operator actions and drivers share: `ALWAYS_DENIED`, `isAllowed`, `overlapsDenied` and `suggestRules`. It will become the `@crane/agent-policy` package, so it imports only `@crane/contracts/rules`, and everything else imports it through `index.ts` (`test/boundaries.test.ts`). The command splitter stays internal and is not a shell parser. `src/agents/policy.ts` and `src/core/permissions.ts` are temporary re-exports; don't add new imports of them. Rule grammar and labels stay in contracts; each driver keeps its own tool lists and CLI arguments.
- `src/agents/` holds drivers behind `AgentDriver`: Claude Code, Codex, simulated. `src/factory/drivers.ts` is the registry. A task's `driver` is the operator's pick (null follows the default setting); an interrupted task resumes on the driver of its last work run, which owns its session. Adding an agent means a driver, an entry in `DRIVER_NAMES` (`packages/contracts/src/types.ts`), and one in `createDriver`. Agents end their final message with a fenced `crane-report` JSON block (asked for in `src/agents/prompts.ts`), parsed by `packages/agent-protocol/src/report.ts`, which owns the fence tag and ignores agent-supplied `validation`. Drivers never import `src/factory/`: plain git calls go through `src/core/git.ts`, and Crane's worktree and branch logic stays in `src/factory/git.ts`. Only the registry imports concrete drivers (`test/boundaries.test.ts` checks both).
- Tasks with autonomy `propose`/`act` run in a git worktree under `$CRANE_HOME/worktrees/<taskId>` on branch `crane/<slug>-<id>`. Crane never pushes or merges on its own. Only an operator's Approve (or Merge) does, and then Crane's own code in `src/factory/merge.ts` lands the branch (merge commit, fast-forward push, local default branch moved only when its checkout is clean). Agents only ever resolve conflicts inside Crane's worktree; they never push or merge.
- `web/` is React + Vite with no UI library. It shares domain/HTTP shapes, labels, and pure helpers with the backend through the internal `@crane/contracts` workspace (`packages/contracts/`). Its explicit entry point is `src/index.ts`; `@crane/contracts/rules` exposes the minimal rule grammar for backend permission handling. Enforcement stays in `src/agent-policy/`. Contracts have no runtime dependencies, Node modules, React, storage, or factory implementation. Cross-workspace source imports are forbidden (`test/contracts.test.ts`).
- `npm run build:packages` compiles contracts, then agent protocol, to JS and declarations before build, typecheck, tests, dev, and the source CLI; `npm run dev` also watches both packages. Run it before invoking backend source scripts directly. The root npm tarball bundles both private packages so installed CLI builds need no separate releases. Package inputs are tracked in `src/core/webbuild.ts`: contracts affect dashboard and factory staleness; agent protocol affects only the factory.

## Rules

- Safety first: nothing an agent does may touch the operator's checkout or default branch. Keep `ALWAYS_DENIED` in `src/agent-policy/denied.ts` intact. Codex has no deny list, so its guard is the sandbox in `codexArgs` (`src/agents/codex.ts`): read-only for investigate-only, workspace-write with no network and no extra writable roots otherwise. Never loosen it. Every new driver needs an equivalent guard. The one place Crane moves a default branch is `landTask` in `src/factory/merge.ts`, after the operator approves: never force-push, and never touch a checkout that has local changes.
- Keep the CLI and web UI at feature parity for operator actions.
- UI work must follow `docs/design.md`. Progressive disclosure is the core principle: show the decision first, the details one tap away.
- Look at UI changes before calling them done. Take screenshots with `npm run screenshot` (wide 1280x800, short 1280x600, and phone 390x844) and read the PNGs; for visual bugs, reproduce in a screenshot first when capture is available. In a sandbox known to refuse local servers or browsers, defer capture directly without trying it. Report visual validation as outstanding and include the changed views, states, exact capture commands, and sizes in an operator checklist, following [Visual review before approval](README.md#visual-review-before-approval). Before approval or merge, the operator must record inspection of the candidate or an explicit waiver with its reason. Passing typecheck, tests, or review and merge checks does not complete visual validation.
- The dashboard on :4471 serves whichever build is newest: Crane's own build of the latest merge to its repo (`$CRANE_HOME/builds/<sha>`, made by `src/factory/dashboard.ts` after each factory-repo merge and on `crane serve`), or the checkout's `web/dist`. If the operator reports that a fixed UI bug is still there, check which build is served (`uiCommit` in `/api/overview`), whether that build failed (a note on the merged task), and whether their tab needs a reload.
- Backend changes need a separate rebuild and restart when `bin/crane.js` runs `dist/`. `/api/overview` reports `factory.factoryOutdated`, and the dashboard shows a notice when the running build is older than its checkout's `src/`. The notice stays until restart even if someone rebuilds on disk. Dashboard builds and page reloads do not update the running backend.
- Copy is sentence case, plain verbs, and names things by what the operator controls. An action keeps its name everywhere ("Approve" → "Approved").
- Before finishing outside the restricted sandbox, run `npm run typecheck` and `npm test` separately and retain each exit status. In Codex's no-network sandbox, run typecheck and relevant direct-file checks from [Sandbox test selection](docs/testing.md#sandbox-test-selection); defer `npm test` and the complete `test/limits.test.ts`, `test/drivers.test.ts`, and `test/restart.test.ts` suites directly to Crane's existing external review and merge checks without attempting them locally. Report them as not run locally, left to Crane's checks; a local subset is not a full-suite pass. Do not change configured checks or reduce their coverage.
- Codex's no-network filter also refuses `listen` and some local socket calls used for piped child stdio. Known incompatible checks do not need another failed attempt to establish this limitation. Direct-file diagnostics are useful only for files that do not require those capabilities; running a fake-agent suite directly does not remove its piped subprocess requirement. Do not reshape tests, scripts, code, permissions, or sandbox settings to get around restrictions. For an unexpected failure, retain the actual error and follow the refusal/reporting rules; missing stream output alone does not prove a code defect or identify an exact sandbox error.
